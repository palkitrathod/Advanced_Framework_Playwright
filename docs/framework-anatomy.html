Anatomy of a Test

Your framework turns three lines of a spec into a browser session by handing work down five layers. This pulls every file apart keyword by keyword — what each word does, what it links to, and what breaks the moment you delete it.

You write this

await loginPage.loginAs(
    'standard_user',
    'tta_secret'
);

One call. No selectors, no URL, no timeouts, no waits.

The browser does this

  1. 01fill [data-test="username"]15s
  2. 02fill [data-test="password"]15s
  3. 03click [data-test="login-button"]15s
  4. 04poll url has /inventory or error shown10s

Every step logged, timed and retried — none of it in your test file.

A

Start here: the same test, written twice

Both versions below log into TTACart and check the form disappeared. Both pass. The difference is what happens to them six months from now.

Without

Raw Playwright

import { test, expect } from '@playwright/test';

test('login works', async ({ page }) => {
  await page.goto(
    'https://app.thetestingacademy.com' +
    '/playwright/ttacart/index.html'
  );
  await page.locator('[data-test="username"]')
    .fill('standard_user');
  await page.locator('[data-test="password"]')
    .fill('tta_secret');
  await page.locator('[data-test="login-button"]')
    .click();
  await expect(
    page.locator('[data-test="login-button"]')
  ).toBeHidden();
});

4 selectors and a hardcoded URL, in the test file. Write a second test and you copy them again. Write twenty and the selector lives in twenty places.

With

Your framework

import { test } from '@playwright/test';
import { LoginPage } from '@pages/LoginPage';

test('login works', async ({ page }) => {
  const loginPage = new LoginPage(page);

  await loginPage.open();
  await loginPage.loginAs(
    'standard_user',
    'tta_secret'
  );
  await loginPage.waitForLoginButtonHidden();
});

Zero selectors, zero URLs, zero timeouts. Reads like the manual test case someone wrote in a spreadsheet. When the app changes, this file does not.

The trade

The right-hand version is shorter, but the code did not vanish — it moved into LoginPage.ts, where it is written once and reused by every test. That is the entire bargain of the Page Object Model, and everything else on this page is detail about how your framework spends it.

B

How the layers got there

Nobody designs five layers up front. Each one exists because the previous version hurt in a specific way. Here is that sequence, with the pain that forced each move.

00

Everything in the test

You write one test. It works. Then you write the second one.

test('login works', async ({ page }) => {
  await page.locator('[data-test="username"]').fill('standard_user');
  await page.locator('[data-test="password"]').fill('tta_secret');
  await page.locator('[data-test="login-button"]').click();
});

test('checkout works', async ({ page }) => {
  // the same three lines again, copied
  await page.locator('[data-test="username"]').fill('standard_user');
  await page.locator('[data-test="password"]').fill('tta_secret');
  await page.locator('[data-test="login-button"]').click();
  // ... then the actual checkout steps
});
What hurts

Every test that needs a logged-in user repeats the login. Rename data-test="username" and you must find and fix all of them — and the compiler cannot help, because they are just strings.

01

Extract the page → LoginPage

Move the selectors and the steps into a class that owns the login screen.

export class LoginPage {
    private readonly usernameInput: Locator;
    private readonly passwordInput: Locator;
    private readonly loginButton: Locator;

    constructor(private page: Page) {
        this.usernameInput = page.locator('[data-test="username"]');
        this.passwordInput = page.locator('[data-test="password"]');
        this.loginButton   = page.locator('[data-test="login-button"]');
    }

    async loginAs(u: string, p: string) {
        await this.usernameInput.fill(u);
        await this.passwordInput.fill(p);
        await this.loginButton.click();
    }
}
Fixed

The selector now exists once. Both tests call loginAs() and neither knows what a data-test attribute is.

What still hurts

Now write InventoryPage, CartPage, and five checkout pages. Each one re-declares private page: Page, each builds its own logger, each writes its own goto(). Seven copies of the same three lines.

02

Extract what every page shares → BasePage

Anything all seven pages need moves up into a parent they all extend.

export abstract class BasePage {
    protected readonly page: Page;
    protected readonly el:   UtilElementLocator;
    protected readonly log:  Logger;

    protected constructor(page: Page, scope: string) {
        this.page = page;
        this.el   = new UtilElementLocator(page, scope);
        this.log  = createLogger(scope);
    }
    protected async goto(path: string) { /* … */ }
}

// LoginPage shrinks to just what is unique about the login screen:
export class LoginPage extends BasePage {
    constructor(page: Page) { super(page, 'LoginPage'); /* … */ }
}
Fixed

Seven page classes now share one copy of the plumbing, and every one gets a logger tagged with its own name for free.

What still hurts

Every action is still a bare locator.click(). There is no logging of what was clicked, and no shared timeout — so when a test fails you get "timeout exceeded" with no record of what it was trying to do.

03

Wrap the actions → UtilElementLocator

One class stands between the pages and Playwright, so logging and timeouts are decided in a single place.

async click(target: Flex, timeout = DEFAULT_ACTION_TIMEOUT_MS) {
    const loc = this.toLocator(target);
    this.log.debug(`Click ${this.describe(target)}`);   // ← now every click is traceable
    await loc.click({ timeout });                     // ← one number governs all of them
}
Fixed

Set LOG_LEVEL=debug and you get a full record of every interaction. Change DEFAULT_ACTION_TIMEOUT_MS once and every wait in the suite retunes.

What still hurts

Every spec still opens with the same ceremony: declare a variable, construct the page in beforeEach, log in, navigate. Tests that need a logged-in user repeat that setup verbatim.

04

Hand the setup over → fixtures

Ask for the state you want by name and Playwright builds it, plus everything it depends on.

// src/fixtures/test-base.ts
loginWithInventory: async ({ validLogin, inventoryPage }, use) => {
    await inventoryPage.assertLoaded();
    await use(inventoryPage);
},

// any spec — no beforeEach, no `new`, no login steps
test('adds an item', async ({ loginWithInventory }) => {
    await loginWithInventory.addToCart('tta-bike-light');
});
Fixed

That test is already logged in and already on the inventory page, because naming the fixture triggered the whole chain: validLogin → loginWithInventory. Playwright builds only the fixtures a test actually names, so nothing is set up that the test does not use.

standard_user is the happy path your login spec uses; locked_out_user is the one the invalidLogin fixture uses to prove the error branch works.

01

Reference: five layers, each ignorant of the next

The rule that makes the whole thing work: a layer may only talk to the layer directly beneath it. Your spec never touches a CSS selector. Your page object never sets a timeout. Nothing but the bottom layer touches the browser.

02

The import lines

Before any class exists, four words at the top of each file decide what the file can see.

src/pages/BasePage.ts — lines 15–17 
import { Page } from "@playwright/test";
import { UtilElementLocator } from "@utils/UtilElementLocators";
import { createLogger, type Logger } from "@utils/logger";
import { Page }

Pulls in Playwright's Page type — the TypeScript description of a browser tab. It is used only to annotate parameters and fields; no value is created from it.

Links tonode_modules/@playwright/test. The same Page object is handed to your test at runtime by Playwright's { page } fixture.

Delete itCompile error on every mention of Page: Cannot find name 'Page'. Tests won't run at all.

"@playwright/test"
not "playwright"

Two different packages exist. playwright is the raw browser-automation library; @playwright/test is the test runner built on top of it, and it is the one that gives you test, expect, fixtures, retries and reporters.

Links toEverything in playwright.config.ts — timeouts, projects, reporters — configures @playwright/test, not playwright.

Delete itImporting from playwright instead gives you a Page that type-checks, but you lose expect's auto-retry and every config value. Waits stop being retried.

"@utils/…"
the @ prefix

A path alias, not a real folder. It stands in for src/utils/ so you never write ../../../utils/logger.

Links totsconfig.json → compilerOptions.paths, where "@utils/*" maps to ["src/utils/*"]. Playwright reads that mapping itself at run time, which is why it works in specs without any extra plugin.

Delete itRemove the entry from tsconfig.json and every aliased import fails with Cannot find module '@utils/logger'. The alias only exists because that config says so.

type Logger

The type keyword marks this import as types only. It is erased entirely when TypeScript compiles — no JavaScript is emitted for it.

Links tosrc/utils/logger.ts, which exports both a value (createLogger) and a type (Logger). One import line takes both, marking which is which.

Delete itDropping just the word type still works here, but the import is no longer guaranteed to vanish at build time — it can drag a real runtime dependency into the output for something you only needed for type-checking.

03

BasePage — dissected

Thirty-six lines every page object is built on. It holds behaviour, never selectors.

src/pages/BasePage.ts 
export abstract class BasePage
{
    protected readonly page: Page;
    protected readonly el:   UtilElementLocator;
    protected readonly log:  Logger;

    protected constructor(page: Page, scope: string)
    {
        this.page = page;
        this.el   = new UtilElementLocator(page, scope);
        this.log  = createLogger(scope);
    }

    protected async goto(relativePath: string): Promise<void>
    {
        await this.page.goto(relativePath);
        await this.page.waitForLoadState("domcontentloaded");
    }
}

The class declaration

export

Makes the class visible outside this file. Without it the class is private to BasePage.ts.

Links toimport { BasePage } from './BasePage' at the top of LoginPage.ts and all six other page objects.

Delete itEvery page object fails to compile: Module '"./BasePage"' has no exported member 'BasePage'. The entire POM layer collapses.

abstract

Declares that this class is incomplete on purpose — it exists to be extended, never instantiated directly.

Links toEvery class X extends BasePage. It is the formal statement of "this is scaffolding".

Delete itNothing breaks immediately, but new BasePage(page, 'x') becomes legal — someone can create a page object that represents no page, with no locators and no open(). The word is a guard-rail, and removing it removes the guard.

The three fields

protected

Visible to this class and its subclasses, invisible to everyone else. This single word is what enforces the whole Page Object discipline.

Links tothis.el and this.log inside LoginPage — a subclass, so allowed. And to your spec, which is not a subclass, so denied.

Delete itFields default to public. A spec could then write loginPage.page.locator('[data-test="username"]').fill('x') — raw selectors leak straight back into test files and the abstraction is worth nothing. This is the most consequential keyword in the file.

readonly

The field may be assigned once, in the constructor, and never reassigned afterwards.

Links toThe three assignments in the constructor body — the only place the compiler permits them.

Delete itA method could later do this.page = someOtherPage, silently re-pointing the page object at a different browser tab mid-test. Failures from that are extremely hard to trace.

: Page
the annotation

Declares the field's type, so the editor knows this.page.goto() exists and this.page.gogo() does not.

Links toThe Page import at the top of the file.

Delete itUnder "strict": true in your tsconfig.json, an un-annotated field with no initialiser is an error. Loosen that and it becomes any — you lose autocomplete and every typo becomes a runtime failure instead of a red squiggle.

The constructor

protected constructor

Only a subclass may call it. Together with abstract this is a second, independent lock on direct instantiation.

Links tosuper(page, 'LoginPage') — a subclass calling up into it.

Delete itIt becomes public. Combined with removing abstract, anyone can instantiate the base class. Alone, abstract still blocks it — the two overlap deliberately.

scope: string

A plain label — the subclass's own name. It is the single most reused value in the framework.

Links toTwo places at once: new UtilElementLocator(page, scope) and createLogger(scope). See the fan-out diagram below.

Delete itEvery log line loses its [LoginPage] tag. Your terminal output becomes an undifferentiated stream where you cannot tell which page emitted which action — the single most useful debugging affordance in the suite.

this.

Refers to the specific object being constructed. this.page = page copies the constructor's parameter onto the instance so other methods can reach it later.

Links toEvery later use — this.el.fill(...) in LoginPage.loginAs reads the field written here.

Delete itWriting page = page assigns the parameter to itself. It compiles, does nothing, and this.page stays undefined — every later call dies with Cannot read properties of undefined.

new

Actually constructs a UtilElementLocator. Each page object gets its own instance, carrying its own scope.

Links toThe UtilElementLocator constructor, which stores the page and builds its own scoped logger.

Delete itthis.el = UtilElementLocator(page, scope) throws at run time: Class constructor cannot be invoked without 'new'.

The goto helper

async

Marks the function as asynchronous — it returns a Promise, and it is allowed to use await inside.

Links toThe await this.goto(...) in LoginPage.open().

Delete itawait inside the body becomes a syntax error. Browser work is inherently asynchronous, so this keyword is not optional.

await

Pauses this function until the Promise settles. It is what makes asynchronous code execute in the order you wrote it.

Links toEvery Playwright call, all of which return Promises.

Delete itThe single most common bug in Playwright code. Without it, page.goto() starts and immediately returns. The next line runs against a page that has not navigated yet. You get flaky failures that pass locally and fail in CI, plus an unhandled promise rejection if it throws.

Promise<void>

The return type. Promise because it is async; <void> because it resolves with no value.

Links toThe caller's await, which unwraps the Promise.

Delete itTypeScript infers it correctly anyway. Purely documentation — but it stops a future edit from silently changing what the method returns.

relativePath
not a full URL

A path fragment like /playwright/ttacart/index.html. Playwright joins it onto baseURL.

Links toresolveBaseURL() in playwright.config.ts, which reads TTA_ENV and BASE_URL from your .env.

Delete itHardcode a full https://… URL instead and the page object is welded to one environment. Switching TTA_ENV=stg would silently keep hitting production.

"domcontentloaded"

Waits until the HTML is parsed — deliberately not waiting for images, fonts or network idle.

Links toIts slower siblings 'load' and 'networkidle'. UtilElementLocator.waitForPageLoad() uses networkidle, wrapped in .catch() precisely because it is unreliable.

Delete itDrop the whole line and goto() may return before the DOM is parsed, so the first locator query can miss. Change it to 'networkidle' and every navigation stalls on background analytics requests.

04

UtilElementLocator — where waiting is decided

BasePage hands every page a this.el. It does three jobs, and the third has a consequence most people miss.

export type Flex = string | Locator;

private toLocator(target: Flex): Locator {
    return typeof target === 'string' ? this.page.locator(target) : target;
}

export const DEFAULT_ACTION_TIMEOUT_MS = 15_000;

async click(target: Flex, timeout = DEFAULT_ACTION_TIMEOUT_MS) {
    const loc = this.toLocator(target);
    this.log.debug(`Click ${this.describe(target)}`);
    await loc.click({ timeout });
}
type Flex =
string | Locator

A union type. The | means "either of these". It lets every method accept a raw CSS string or an already-built Playwright Locator.

Links totoLocator(), which normalises whichever form arrived. LoginPage always passes the second form — objects built once in its constructor.

Delete itAccept only string and page objects can no longer pass their pre-built locators — every call site would rebuild locators from strings, losing Playwright's chaining and .filter() features. Accept only Locator and quick one-off calls get verbose.

private

Visible only inside this class — stricter than protected, which also allows subclasses.

Links toOnly the methods in this same file. toLocator is plumbing nobody else should call.

Delete itIt becomes public API you now have to keep stable. Callers could bypass the logging and timeout wrapper entirely by calling toLocator and acting on the result directly.

15_000
the underscore

A numeric separator — pure readability. 15_000 and 15000 are the identical number to JavaScript.

Links toEvery method's default parameter, and therefore every element interaction in the entire suite.

Delete itNothing — it is cosmetic. But delete the whole constant and every timeout has to be written out at each call site, so tuning them means editing dozens of lines instead of one.

timeout =
DEFAULT_ACTION…

A default parameter. Callers may pass their own timeout; almost none do, so the constant applies nearly everywhere.

Links toThe one place a page object might override it for a genuinely slow control.

Delete itEvery caller must now pass a timeout explicitly, or you fall back to Playwright's global default — and you lose the single knob that controls all element waits.

{ timeout }

Object shorthand for { timeout: timeout }. This is the line that makes the framework's timeout win over Playwright's configured default, because an explicit option always beats a config value.

Links toexpect: { timeout: 10_000 } in playwright.config.ts — which this overrides. See the budget diagram below.

Delete itAll element waits fall back to the config's timeouts. Arguably simpler — but DEFAULT_ACTION_TIMEOUT_MS would then be dead code that appears to do something and does not.

Its waits are assertions in disguise

async waitForHidden(target: Flex, timeout = DEFAULT_ACTION_TIMEOUT_MS) {
    await expect(this.toLocator(target)).toBeHidden({ timeout });
}
Why this matters

This is not page.waitForTimeout(15000), which would sleep blindly for fifteen seconds every time. expect().toBeHidden() re-checks continuously and returns the instant the condition is true — usually in milliseconds — and only fails if the full budget expires.

Replace it with a fixed sleep and your suite gets slower and flakier at once: slower because it always waits the maximum, flakier because a slow environment still blows past the fixed number with no retry.

LoginPage — dissected

src/pages/LoginPage.ts 
export class LoginPage extends BasePage {

    static readonly PATH = '/playwright/ttacart/index.html';

    private readonly usernameInput: Locator;
    private readonly passwordInput: Locator;
    private readonly loginButton:   Locator;
    private readonly errorBox:      Locator;

    constructor(page: Page) {
        super(page, 'LoginPage');
        this.usernameInput = page.locator('[data-test="username"]');
        this.passwordInput = page.locator('[data-test="password"]');
        this.loginButton   = page.locator('[data-test="login-button"]');
        this.errorBox      = page.locator('[data-test="error"]');
    }

    async open(): Promise<void> {
        this.log.info("Open login pgae");
        await this.goto(LoginPage.PATH);
    }
extends BasePage

Inherits everything BasePage declares — page, el, log, goto() — without redeclaring any of it.

Links toBasePage.ts, and to the six sibling page objects that extend the same base.

Delete itthis.el, this.log and this.goto all become Property does not exist errors, and super() is illegal. You would have to hand-build a logger and an element wrapper in every page class — the duplication POM exists to prevent.

static

Puts PATH on the class, not on each instance. Read it as LoginPage.PATH without constructing anything.

Links tothis.goto(LoginPage.PATH) inside open(), and any other file that wants to know the login URL.

Delete itIt becomes an instance field, so reading it requires an object first. Note the code says LoginPage.PATH, not this.PATH — remove static without changing that reference and it stops compiling.

private readonly
usernameInput

The selector lives here and only here. private hides it from specs; readonly pins it after construction.

Links tothis.el.fill(this.usernameInput, username) in loginAs. Nothing outside this file can name it.

Delete privateA spec could reach in with loginPage.usernameInput.fill('x'), and the selector's blast radius grows from one file to every file that does so.

[data-test="…"]

An attribute selector aimed at a dedicated test hook, rather than at a CSS class or DOM position.

Links toAttributes in the TTACart markup that exist purely for automation.

Use CSS insteadTarget .btn-primary or div > form > input:nth-child(2) and your test breaks the next time someone restyles the page or reorders a field. data-test attributes change only when someone deliberately changes them.

super(page,
'LoginPage')

Calls the parent constructor. It must be the first statement — TypeScript forbids touching this before it runs.

Links toBasePage's constructor, which uses that second argument as the scope for both the logger and the element wrapper.

Delete it'super' must be called before accessing 'this'. Move it below the locator assignments and you get the same error — the order is enforced, not stylistic.

page.locator(…)
in the constructor

Builds a locator, which queries nothing. A Playwright Locator is a lazy description — "how to find this element when asked". The DOM lookup happens at .fill() or .click() time.

Links toEvery this.el.* call that later resolves it against whatever the page currently shows.

Why it mattersBecause nothing is resolved up front, locators never go stale across navigations, and building five of them in a constructor is free. An older tool like Selenium returns a live element reference here, which does go stale — hence its classic StaleElementReferenceException.

The most interesting method in the file

async loginAs(username: string, password: string) {
    this.log.info(`loginAs ${username}`);
    await this.el.fill(this.usernameInput, username);
    await this.el.fill(this.passwordInput, password);
    await this.el.click(this.loginButton);

    // wait until the page settles — either way
    await expect.poll(async () => (
        this.page.url().includes('/inventory') || await this.errorBox.isVisible()
    )).toBe(true);
}
expect.poll

Re-runs the function you give it every ~100ms until it returns the expected value or the budget expires. Unlike plain expect, it re-invokes your own code, not just a locator query.

Links toexpect: { timeout: 10_000 } in playwright.config.ts — this call passes no explicit timeout, so it inherits the config value.

Delete itloginAs returns the moment the click dispatches, while the browser is still mid-navigation. The very next line races the page. This is the classic source of "passes locally, fails in CI".

||

The design decision of the whole file. It makes either outcome — logged in, or rejected with an error — end the wait.

Links toThe invalidLogin fixture in src/fixtures/test-base.ts, which logs in as locked_out_user and expects the error banner. It reuses this exact method.

Delete itWait only for /inventory and the negative-login fixture hangs for the full 10s and then fails — even though it behaved exactly as intended. The method would no longer be reusable for failure cases.

.toBe(true)

The condition the poll is waiting to see. It converts "keep checking" into a concrete pass/fail.

Links toThe boolean the polled arrow function returns.

Delete itexpect.poll(...) alone never executes — it builds an assertion object and discards it. The wait silently does nothing, and you would never know.

The spec — dissected

const log = …
at module scope

Sits outside every function, so it runs once when the file is imported — not per test. Tags this file's own messages [login.spec], distinct from [LoginPage].

Links tocreateLogger in src/utils/logger.ts, the same factory BasePage uses.

Delete itYou lose the ability to see control passing between spec and page in the log stream. Everything would carry the page's tag, hiding which layer initiated what.

test.describe

Groups related tests under a shared title and creates a scope that beforeEach applies to.

Links toReport headings, and the --grep filter, which matches against the full title including the describe prefix.

Delete itTests still run, but any beforeEach now applies to the whole file, and the report loses its grouping. With one test the cost is small; with twenty it is not.

let loginPage

let because the value is reassigned in every beforeEach. It is declared in the describe scope so both the hook and the test body can see the same variable.

Links toThe assignment in beforeEach and the reads in the test body.

Use constCannot assign to 'loginPage' because it is a constant. Declare it inside beforeEach instead and the test body cannot see it at all — Cannot find name 'loginPage'.

{ page }
the destructuring

Not ordinary destructuring — this is a fixture request. Playwright inspects the parameter names you write and creates exactly those fixtures. Naming page is what causes a fresh browser context and tab to be built for this test.

Links toPlaywright's built-in fixtures, and to your own in src/fixtures/test-base.ts — which is how the e2e specs ask for { loginPage } directly and skip the manual new.

Delete itNo page is created at all — Playwright builds only what you name. new LoginPage(page) then fails with page is not defined. Conversely, naming a fixture you do not use still pays its setup cost.

beforeEach
not beforeAll

Runs before every test, rebuilding the page object each time — necessary because each test gets a different page.

Links toPlaywright's per-test isolation: a fresh BrowserContext with empty cookies and localStorage.

Use beforeAllThe page object would be built once against the first test's page, which is closed before the second test runs. Every subsequent test fails with Target page, context or browser has been closed.

async () =>

An arrow function marked async. Arrow syntax matters: it does not rebind this, so surrounding scope stays intact.

Links toEvery await inside the body.

Delete asyncEvery await in the body becomes a syntax error. Worse, if you also drop the awaits, the test function returns immediately — Playwright marks it passed while the browser work is still running. A test that always passes and tests nothing.

test.step

Purely for reporting — it does not change execution. It creates the collapsible tree in the HTML report and the ✅ lines your CustomReporter prints.

Links tosrc/utils/visualStep.ts, which wraps test.step to attach a screenshot per step when ATTACH_SCREENSHOTS=true. Also to the trace viewer's timeline.

Delete itThe test still passes identically. You lose the labelled breakdown in the report, so a failure points at a bare line number instead of "Login as standard_user".

@p0
in the title

A tag. It carries no special syntax — it is just text in the title that a filter can match.

Links tonpm test -- --grep @p0, and to CI configs that run only the critical subset.

Delete itThe test drops out of every --grep @p0 run — including, silently, any CI job that filters on it. It would stop being executed without anything reporting an error.

The one that bites hardest

Of everything on this page, the missing await is the failure you will actually meet. A test with no await finishes before the browser does, so Playwright records a pass for work that never completed — or that failed after the verdict was already written.

D

Worked example: add a page yourself

The real test of understanding a framework is adding to it. Here is a complete new page object — every file you touch, in order.

Say TTACart gains an Order History screen listing past orders, and you need a test that checks a completed order shows up.

Step 1 — the page object

src/pages/OrderHistoryPage.ts — new file 
import { expect, Locator, Page } from '@playwright/test';
import { BasePage } from './BasePage';

export class OrderHistoryPage extends BasePage {

    // 1. the URL, relative so it follows TTA_ENV
    static readonly PATH = '/playwright/ttacart/orders.html';

    // 2. selectors — private, so no spec can reach them
    private readonly title:    Locator;
    private readonly rows:     Locator;
    private readonly orderIds: Locator;

    constructor(page: Page) {
        super(page, 'OrderHistoryPage');   // ← first, and the log tag
        this.title    = page.locator('[data-test="title"]');
        this.rows     = page.locator('[data-test="order-row"]');
        this.orderIds = page.locator('[data-test="order-id"]');
    }

    // 3. actions — public, and they use this.el, never this.page
    async open(): Promise<void> {
        this.log.info('Opening order history');
        await this.goto(OrderHistoryPage.PATH);
    }

    async assertLoaded(): Promise<void> {
        await this.el.waitForVisible(this.title);
    }

    async rowCount(): Promise<number> {
        return this.el.count(this.rows);
    }

    async allOrderIds(): Promise<string[]> {
        return this.el.getAllTexts(this.orderIds);
    }
}

Every method here is built from things BasePage handed over. You wrote no logger, no timeout, no navigation helper — waitForVisible, count and getAllTexts already exist on this.el.

Step 2 — register the fixture

src/fixtures/test-base.ts — three edits 
// a) import it
import { OrderHistoryPage } from '@pages/OrderHistoryPage';

// b) add it to the fixture type
export type TestFixture = {
    // … the existing seven …
    orderHistoryPage: OrderHistoryPage;
};

// c) provide it
export const test = base.extend<TestFixture>({
    // … the existing ones …
    orderHistoryPage: async ({ page }, use) => {
        await use(new OrderHistoryPage(page));
    },
});
Miss this step and

Everything still works — you just write new OrderHistoryPage(page) by hand in each spec, exactly as login.spec.ts does today. The fixture is what lets specs skip that.

Step 3 — the test

src/tests/orders/order-history.spec.ts — new file 
import { test, expect } from '@fixtures/test-base';
import { createLogger } from '@utils/logger';

const log = createLogger('order-history.spec');

test.describe('@P1 TTACart - Order history', () => {

    test('shows an order after checkout', async ({
        loginWithSelectedItem,      // ← logged in, one item already in the cart
        cartPage,
        checkoutStepOnePage,
        checkoutStepTwoPage,
        orderHistoryPage,           // ← the fixture you just added
    }) => {

        await test.step('Complete an order', async () => {
            await cartPage.open();
            await cartPage.checkout();
            await checkoutStepOnePage.fillCustomerInfo('Palkit', 'Rathod', '380001');
            await checkoutStepTwoPage.finish();
        });

        await test.step('Order appears in history', async () => {
            log.info('Checking order history');
            await orderHistoryPage.open();
            await orderHistoryPage.assertLoaded();
            expect(await orderHistoryPage.rowCount()).toBeGreaterThan(0);
        });
    });
});

Read that test back: it never mentions a selector, a URL, a timeout or a login. It says what a human tester would say. The loginWithSelectedItem fixture silently performed a login, an inventory load and an add-to-cart before the first line ran.

Extend BasePage · call super(page, 'ClassName') first · private readonly locators · static readonly PATH, relative · public actions built on this.el · register the fixture.

09

Seams worth knowing about

Four things true of this code today. None are breakage — they're where the framework is still settling.

  • Trap

    Two timeout sources, not one

    expect: { timeout: 10_000 } governs the poll inside loginAs — but not any this.el.* wait, because those pass an explicit 15s. Tuning means editing both playwright.config.ts and DEFAULT_ACTION_TIMEOUT_MS.

  • Style

    This spec doesn't use your fixtures

    login.spec.ts imports test from @playwright/test and calls new LoginPage(page) by hand, while your e2e specs import from @fixtures/test-base and ask for { loginPage }. Both work — the README frames this as the deliberate "plain page-object" contrast — but two styles now coexist.

  • Style

    Credentials are hardcoded here

    The spec passes 'standard_user', 'tta_secret' literally, though src/config/credentials.ts exists for exactly this and already defaults to those values. Your e2e specs use credentials.standardUser, so this one file would not follow a .env override.

  • Dead

    Two unused bindings

    page is destructured in the test body but never referenced — it was needed before the assertion moved into waitForLoginButtonHidden(). And loginCredentialsHint is declared in LoginPage and used nowhere. Both harmless; removing them changes nothing.

Adding a new page, in order

  1. Create src/pages/YourPage.ts extending BasePage.
  2. Call super(page, 'YourPage') first — that name becomes your log tag.
  3. Declare private readonly locators and a static readonly PATH.
  4. Expose public actions that use this.el, never raw this.page.
  5. Register a fixture in src/fixtures/test-base.ts so specs never call new.
