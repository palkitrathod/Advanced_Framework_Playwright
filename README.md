# Advanced Framework Playwright

A TypeScript-based test automation framework built on [Playwright](https://playwright.dev/), scaffolded for scalable UI + API testing with page objects, fixtures, schema validation, and reporting.

## Framework Overview

This is a hybrid **UI + API test automation framework** built around Playwright's test runner and the **Page Object Model (POM)** pattern. Key characteristics:

- **Page Object Model** — every page of the app under test is a class extending a shared `BasePage`, which injects a Playwright `Page`, an element-action wrapper, and a scoped logger
- **Fixture-driven setup** — `src/fixtures/test-base.ts` exports a custom `test` that hands each spec a ready-built page object, plus composable *state* fixtures (`validLogin`, `loginWithInventory`, `loginWithSelectedItem`, `invalidLogin`) so specs skip repetitive setup
- **Multi-environment aware** — `TTA_ENV` selects between `qa`, `stg`, `prod`, and `dev` base URLs, resolved automatically in `playwright.config.ts`
- **Data-driven** — test data can be sourced from CSV, XLSX, or JSON (via `csv-parse`, `xlsx`, `jsonpath-plus`), with synthetic data generated by `@faker-js/faker`
- **API testing, in four layers** — `src/tests/apisTests/` walks the same Restful Booker API up an abstraction ladder: raw `request` calls → a generic `ApiHelper` → a typed `BookingApi` service object with a fixture-supplied token → JSONPath reads. All of it runs under `npm test`. `ajv`/`ajv-formats` are installed for JSON schema validation but not yet used. See [API Testing](#api-testing)
- **Custom reporting & logging** — a custom Playwright reporter (`src/utils/CustomReporter.ts`) generates a standalone, tabbed HTML report (`tta-report/`) with test results, screenshot/video/trace artifacts, and AI/flaky-analysis panels, alongside the built-in HTML/list reporters and Winston-based logging
- **AI-assisted analysis (optional, currently stubbed)** — `src/ai/` holds hooks the reporter calls for root-cause analysis on failures and flaky-test detection between runs; see [AI-Assisted Analysis](#ai-assisted-analysis-optional) below
- **Clean imports** — TypeScript path aliases (`@pages/*`, `@api/*`, `@fixtures/*`, etc.) avoid deep relative import chains
- **CI-integrated** — GitHub Actions runs the suite on every push/PR to `main`/`master` and uploads the HTML report as a build artifact

## Tech Stack

- **Playwright** (`@playwright/test`) — end-to-end test runner (Chromium, Firefox, WebKit)
- **TypeScript** — with path aliases for clean imports
- **Allure Playwright** — installed as a dependency, but not yet registered in `playwright.config.ts`'s `reporter` array; add `['allure-playwright']` there to enable it
- **Winston** — logging
- **Ajv / Ajv-formats** — JSON schema validation (useful for API response checks)
- **dotenv** — environment variable management
- **@faker-js/faker** — test data generation
- **csv-parse**, **xlsx**, **jsonpath-plus** — external/data-driven test data support

Page objects extend a shared `BasePage` (`src/pages/BasePage.ts`), which supplies the Playwright `Page` handle, a `UtilElementLocator` (`this.el`) for actions, a scoped Winston logger (`this.log`), and a `goto()` helper that respects `baseURL`. The implemented page classes (`LoginPage`, `InventoryPage`, `ItemDetailPage`, `CartPage`, `CheckoutStepOnePage`, `CheckoutStepTwoPage`, `CheckoutCompletePage`) cover a SauceDemo-style storefront flow (login → inventory → item detail → cart → 3-step checkout).

## Custom Fixtures

There are two fixture files, one per suite. UI specs import `test`/`expect` from `@fixtures/test-base`; API specs import them from `@fixtures/booker.fixture`. Either way, never from `@playwright/test` directly.

### UI fixtures — `@fixtures/test-base`

That custom `test` provides two kinds of fixtures:

**Page-object fixtures** hand over a constructed page object without navigating anywhere: `loginPage`, `inventoryPage`, `itemDetailPage`, `cartPage`, `checkoutStepOnePage`, `checkoutStepTwoPage`, `checkoutCompletePage`.

**State fixtures** perform reusable setup, and compose into a chain — Playwright only builds the one a test actually asks for, plus its dependencies:

| Fixture | Provides |
|---|---|
| `invalidLogin` | Logs in as `locked_out_user` and asserts the error banner is visible (independent negative state) |
| `validLogin` | Logs in as `standard_user` and waits for the login form to disappear |
| `loginWithInventory` | `validLogin` → asserts the inventory page has loaded |
| `loginWithSelectedItem` | `loginWithInventory` → adds one known item to the cart |

```ts
import { test, expect } from '@fixtures/test-base';

test('add to cart', async ({ inventoryPage, cartPage }) => {
    await inventoryPage.open();
    await inventoryPage.addToCart('tta-bike-light');
    await cartPage.open();
    expect(await cartPage.rowCount()).toBe(1);
});
```

Login accounts come from `src/testdata/logintestdata.json`; `test-base.ts` fails fast at import time if `standard_user` or `locked_out_user` is missing from that file.

### API fixtures — `@fixtures/booker.fixture`

| Fixture | Provides |
|---|---|
| `bookingApi` | A `BookingApi` client built on the test's `request` context |
| `bookerToken` | A live token from `POST /auth`, resolved before the test body runs |

```ts
import { test, expect } from '@fixtures/booker.fixture';
import { buildBookingFromGenerator } from '@testdata/booking.data';

test('create a booking', async ({ bookingApi }) => {
    const { bookingid, booking } = await bookingApi.createBooking(buildBookingFromGenerator());
    expect(bookingid).toBeGreaterThan(0);
    expect(booking.firstname).toBeTruthy();
});
```

Ask for `bookerToken` only when you need the token *value* — to log it, pass it on, or assert on it.
Mutating calls manage their own token, and recover from a 403, when you omit the argument.

## Environment Configuration

Environment variables are managed with `dotenv` and loaded automatically in `playwright.config.ts` from a `.env` file at the project root. `.env` is git-ignored, so each environment (local machine, CI, etc.) keeps its own copy.

Create a `.env` file in the project root with the following keys:

```
TTA_ENV=qa
BASE_URL=
QA_BASE_URL=
STG_BASE_URL=
PROD_BASE_URL=
DEV_BASE_URL=
API_BASE_URL=
LOG_LEVEL=info
TEST_ENV=QA
TEST_AUTHOR=
STANDARD_USER=standard_user
TTA_SECRET=tta_secret
CHECKOUT_ITEM_ID=test-allthethings-tshirt-red
ATTACH_SCREENSHOTS=false
```

| Variable | Required | Description |
|---|---|---|
| `TTA_ENV` | no | Active environment key used to select which `*_BASE_URL` to run against (e.g. `qa`, `stg`, `prod`, `dev`). Defaults to `qa` |
| `BASE_URL` | no | Explicit base URL for the app under test. When set it wins over every `*_BASE_URL` below |
| `QA_BASE_URL` | no | Base URL for the QA environment |
| `STG_BASE_URL` | no | Base URL for the Staging environment |
| `PROD_BASE_URL` | no | Base URL for the Production environment |
| `DEV_BASE_URL` | no | Base URL for local/dev environment (e.g. `http://localhost:3000`) |
| `API_BASE_URL` | no | Base URL for API test requests |
| `LOG_LEVEL` | no | Winston log verbosity (e.g. `info`, `debug`, `warn`, `error`) |
| `TEST_ENV` | no | Environment label used in test reports/logs |
| `TEST_AUTHOR` | no | Author tag used in test reports/logs |
| `STANDARD_USER` | no | Login username. Read via `envOr`, so it falls back to `standard_user` |
| `TTA_SECRET` | no | Login password. Read via `envOr`, so it falls back to `tta_secret` |
| `CHECKOUT_ITEM_ID` | **yes**¹ | Product id the env-driven checkout spec adds to the cart |
| `ATTACH_SCREENSHOTS` | no | Set to `true` to make `visualStep()` attach a screenshot to the report after every step |

¹ Required only by `src/tests/e2e/e2e-checkout-env.spec.ts`, which also calls `assertEnv('STANDARD_USER', 'TTA_SECRET')`. These three are validated **at file load**, so if any is missing that spec throws during collection and **the entire run aborts before a single test executes** — not just that one file, and not just the UI suite. Set all three in `.env` to fix it.

That spec has a second, separate gap: it calls `DataGenerator.checkoutCustomerFromEnv()`, which is not defined anywhere. Adding the three `.env` keys unblocks collection for every other spec, but this one will then fail at runtime until that method exists — reading `CHECKOUT_FIRST_NAME` / `CHECKOUT_LAST_NAME` / `CHECKOUT_POSTAL_CODE` with Faker fallbacks would match the rest of the file.

> Note that `--grep`/`--grep-invert` will *not* get you past this: Playwright imports every spec file to enumerate its tests, so the throw happens before any filtering applies. To run the suite without that spec you have to keep it from being loaded at all — pass the other paths explicitly:
>
> ```bash
> npm test -- src/tests/login src/tests/e2e/e2e-checkout.spec.ts src/tests/e2e/e2e-checkout_new_fixture.spec.ts
> ```

`.env` is git-ignored and never committed — treat `STANDARD_USER`/`TTA_SECRET` and any future secrets as environment-specific and set them locally (or as CI secrets), not in source control.

> **Why `STANDARD_USER`/`TTA_SECRET` and not `USERNAME`/`PASSWORD`:** `dotenv` never overwrites a variable that already exists in the environment, and `USERNAME` in particular is set globally by many shells and CI runners — the pre-existing value would silently win over the `.env` entry. The prefixed names are collision-proof. Reference these values through `src/config/env.ts` (`requireEnv` / `envOr` / `assertEnv`) rather than reading `process.env` directly, and add new variables to the table above as the framework grows.

## Path Aliases

Configured in `tsconfig.json` (`compilerOptions.paths`) for cleaner, absolute-style imports instead of long relative paths (`../../../utils/...`):

| Alias | Path |
|---|---|
| `@api/*` | `src/api/*` |
| `@config/*` | `src/config/*` |
| `@fixtures/*` | `src/fixtures/*` |
| `@pages/*` | `src/pages/*` |
| `@testdata/*` | `src/testdata/*` |
| `@utils/*` | `src/utils/*` |

Example usage:

```ts
import { test, expect } from '@fixtures/test-base';
import { LoginPage } from '@pages/LoginPage';
import { credentials } from '@config/credentials';
import { UtilElementLocator } from '@utils/UtilElementLocators';
import { DataGenerator } from '@utils/DataGenerator';
```

Note there is no alias for `src/ai/*` — the reporter reaches those modules by relative path.

> Note: `tsconfig.json` paths are used for type-checking and editor IntelliSense. Playwright resolves them at test-run time too, so the aliases work in specs as-is. If you introduce a build step or ship compiled JS, ensure alias resolution also works there (e.g. via `tsconfig-paths` or a bundler).

> **Known issue — `tsc` cannot type-check this project as configured.** `package.json` pins `typescript: ^7.0.2`, but `tsconfig.json` still uses `moduleResolution: "node"` (node10) and `baseUrl`, both of which TypeScript 7 **removed**. Running `npx tsc --noEmit` fails with `TS5108`/`TS5102`/`TS5090` before it checks a single source file. This does not affect `npm test` — Playwright transpiles specs itself and honours `paths` independently. To restore type-checking, either pin TypeScript back to `^5.x`, or migrate the config to `"moduleResolution": "bundler"` with `baseUrl` dropped and each alias rewritten as a relative path (`"@pages/*": ["./src/pages/*"]`).

## Test Configuration

Defined in `playwright.config.ts`:

- **Test directory**: `./src/tests`
- **Base URL**: resolved from `TTA_ENV` (falls back to `BASE_URL`, then the matching `*_BASE_URL` for `qa`/`stg`/`prod`/`dev`/`api`)
- **Browsers/projects**: Chromium (Desktop viewport)
- **Timeouts**: `60s` per test, `10s` for expect assertions
- **Parallelization**: `fullyParallel: true`
- **Retries**: `0` locally, `2` on CI (`process.env.CI`)
- **Reporters**: HTML, list, and a custom reporter (`src/utils/CustomReporter.ts`, see [Custom Reporter](#custom-reporter) below)
- **Tracing/screenshots/video**: trace and video captured on every run; screenshots on failure only
- **Environment loading**: `.env` is loaded via `dotenv` before the config is evaluated, resolved as `path.resolve(__dirname, '.env')` so it is found regardless of the current working directory

## API Testing

`src/tests/apisTests/` holds request-level tests against the [Restful Booker](https://restful-booker.herokuapp.com/)
demo API. They use Playwright's built-in `request` fixture, so no browser is launched. They live inside
`testDir`, so the runner discovers them alongside the UI specs — no config change needed.

> Note: a bare `npm test` currently collects **0 tests**, because `e2e-checkout-env.spec.ts` throws at
> file load while `.env` is missing three keys — that aborts collection for the whole run, API specs
> included. See [footnote 1 under Environment Configuration](#environment-configuration). Passing a path
> (as below) sidesteps it, because only matching files are imported.

The four folders are a deliberate ladder: each level removes a pain the level below it has.

| Level | Folder | What it demonstrates | Pain it removes |
|---|---|---|---|
| 1 | `01_restfulbooker_raw/` | Raw `request.get/post/put`, with URLs, headers and payloads inline, plus one `request.newContext()` demo | — (the baseline) |
| 2 | `02_restfulbooker_apiHelper/` | The same calls through `ApiHelper` | Every spec re-writing header/verb boilerplate |
| 3 | `03_restfulbooker_fixture_e2e_api/` | `BookingApi` service object, handed over by `booker.fixture.ts` | Specs knowing endpoint paths, and re-minting tokens |
| 4 | `04_jsonpath_plus/` | Deep response reads with `jsonpath-plus` | Long chains of optional property access |

### The building blocks

**`src/utils/ApiHelper.ts`** — a generic HTTP wrapper. It accepts either a `Page` or an
`APIRequestContext` (its `ApiContext` type), so the same helper works in a UI spec and an API spec. A single
`callApi({url, method, headers, data, params, timeout})` covers all five verbs, with `get/post/put/patch/delete`
convenience methods on top, plus:

- `callApiWithRetry(options, {condition, pollingInterval, retryCount})` — re-issues a request until a
  predicate on the response passes. For endpoints that are eventually consistent.
- `parseJsonResponse<T>(response)` — a typed `response.json()`.
- `isSuccess(response)` / `isFailureClient(response)` — 2xx and 4xx range checks.

**`src/api/BookingApi.ts`** — a service object that knows Restful Booker's endpoints so specs don't
have to. It exports the `Booking`, `BookingDates`, `CreateBookingResponse` and `BookingFilters` types, and:

- **Managed token.** `getToken()` mints one on first use and caches it; `getToken(true)` or
  `invalidateToken()` forces a re-auth.
- **403 recovery.** Restful Booker answers an expired or unknown token with `403`, never `401`. Omit the
  `token` argument on a mutating call and `sendAuthed()` re-auths and retries once on a 403. Pass a token
  explicitly and it is used as-is — which is exactly what the negative specs rely on to assert a rejection.
- **Two flavours per verb.** `getBooking(id)` returns a typed `Booking` and *throws* on a non-2xx;
  `getBookingResponse(id)` hands back the raw `APIResponse` so a spec can assert on a failure status.
  Create and update have the same split.
- Base URL and credentials are constructor arguments defaulting to `https://restful-booker.herokuapp.com`
  and `admin` / `password123`, so this layer does **not** depend on Playwright's `baseURL`.

**`src/fixtures/booker.fixture.ts`** — the API counterpart to `test-base.ts`. The `bookingApi` fixture
builds the client once per test; `bookerToken` resolves a real token before the test body runs. A fixture
resolves once, so it cannot react to a token that expires mid-test — that recovery lives in `sendAuthed()`.

**`src/testdata/booking.data.ts`** — payload builders. `buildBookingFromGenerator()` produces a fully
random booking whose check-out is derived from its check-in (so a stay is never inverted) and whose
check-in is relative to today (so a booking never ages into the past). `buildBooking()` is the same thing
with check-in pinned to `PINNED_CHECKIN`, for the JSONPath spec that asserts on a literal date. All
randomness comes from `DataGenerator`, which grew four primitives to support this: `number(min, max)`,
`bool()`, `oneOf(items)` and `dateOffset(days, from?)`.


On Windows PowerShell, set the variable first: `$env:BASE_URL='https://restful-booker.herokuapp.com'`.

### Caveat: `01_basic_ping.spec.ts` depends on `baseURL`

That one spec calls `request.get("/ping")` with no host, so it resolves against Playwright's `baseURL`.
But `resolveBaseURL()` checks `BASE_URL` **first**, before it ever looks at `TTA_ENV`:

```ts
if (process.env.BASE_URL) return process.env.BASE_URL;   // ← wins unconditionally
const env = (process.env.TTA_ENV || 'qa').toLowerCase();
switch (env) { case 'api': return process.env.API_BASE_URL || '…'; /* … */ }
```

`.env` sets `BASE_URL=https://app.thetestingacademy.com`, so **`TTA_ENV=api` can never take effect** and
the `case 'api'` branch is unreachable. The ping goes to the storefront host, which answers `200`
instead of `201`:

```
Error: expect(received).toBe(expected)
Expected: 201
Received: 200
```

So on a plain `npm test -- src/tests/apisTests` this is the one spec that fails; override `BASE_URL` for
the run (as above) and it passes. Every other API spec is unaffected, because none of them rely on the
config's `baseURL`: levels 1–2 build absolute URLs inline, levels 3–4 go through `BookingApi` (which
carries its own base URL), and `03_newcontext_api.spec.ts` sets a `baseURL` on its own request context.

Two ways to fix it properly, in order of preference:

```ts
// Option A — give the API tests their own project with their own baseURL.
// Also keeps browser-only settings (video, trace, screenshot) off the API run.
projects: [
  { name: 'chromium', testDir: './src/tests', use: { ...devices['Desktop Chrome'] } },
  { name: 'api',      testDir: './src/tests/apisTests',
    use: { baseURL: process.env.API_BASE_URL || 'https://restful-booker.herokuapp.com' } },
],

// Option B — let TTA_ENV win over BASE_URL inside resolveBaseURL(),
// so `TTA_ENV=api` actually selects API_BASE_URL.
```

Option A is the smaller change, and it lets you run `npm test -- --project=api`.

## Custom Reporter

`src/utils/CustomReporter.ts` implements a self-contained "TTA" HTML reporter (`CustomTTAReporter`, registered as a default export and wired up in `playwright.config.ts`). Per run it writes to `tta-report/`:

- `report_<timestamp>.html` — the full standalone report for that run
- `index.html` — redirects to the most recent report, so it's safe to bookmark
- `history.html` — index of past runs
- `traces/`, `videos/` — per-test artifacts copied out of Playwright's results

The report body is tabbed — **Test Results**, **AI Data**, **AI Verdict**, and **Flaky** — so failure analysis sits alongside the run results rather than in a separate tool.

It also writes a run snapshot to `reports/runs/<runId>.json` so the next run can diff against it for flaky detection (see [AI-Assisted Analysis](#ai-assisted-analysis-optional)).

To the console it prints a run header, a live per-test result line as each test finishes, the flaky-analyzer verdict, and a final summary table (pass/fail/skip counts, duration, pass rate).

### Viewing the report

```bash
open tta-report/index.html          # macOS — always the latest run
```

Embedded videos may be blocked by the browser over `file://`. If so, serve the folder over HTTP instead:

```bash
npx serve tta-report
```

Traces aren't viewable from the report directly — open them with Playwright's trace viewer:

```bash
npx playwright show-trace tta-report/traces/trace_1.zip
```

`tta-report/`, `reports/`, `logs/`, `playwright-report/`, and `test-results/` are all git-ignored — every run appends a timestamped report, trace/video artifacts, a run snapshot, and log output.

## Utilities

- **`UtilElementLocators.ts`** — `UtilElementLocator`, a thin wrapper around Playwright actions (`click`, `fill`, `waitForHidden`, selects, …). Every page object gets one as `this.el`, scoped to the page name so actions are logged with their origin.
- **`logger.ts`** — `createLogger(scope)` returns a Winston logger tagged with that scope. Used by page objects (`this.log`) and directly in specs. Verbosity is controlled by `LOG_LEVEL`; output is written to `logs/`. See `KBlogger.md` for notes on the setup.
- **`ApiHelper.ts`** — `ApiHelper`, a generic HTTP wrapper usable from either a `Page` or an `APIRequestContext`. One `callApi()` for every verb, convenience methods per verb, retry-until-condition, typed JSON parsing, and status-range checks. See [API Testing](#api-testing).
- **`DataGenerator.ts`** — Faker-backed synthetic data: credentials, checkout customer info, and full profiles, plus the primitives `number(min, max)`, `bool()`, `oneOf(items)` and `dateOffset(days, from?)` used to build API payloads.
- **`visualStep.ts`** — a drop-in replacement for `test.step` that also captures a screenshot at the end of the step and attaches it to the TTA report. Screenshots are only taken when `ATTACH_SCREENSHOTS=true`, so the default run pays no cost.

  ```ts
  await visualStep(page, 'Open the cart', async () => {
      await cartPage.open();
  });
  ```

## AI-Assisted Analysis (optional)

`CustomReporter.ts` can enrich the report with AI-generated context for failed and flaky tests, but everything under `src/ai/` is currently a **stub** — the hooks are wired up and called by the reporter, though no real LLM backend is configured yet.

- **`src/ai/config/providers.ts`** — `hasApiKey()` is the single gate the reporter checks before calling any LLM path. It currently always returns `false`, so AI calls are skipped by design until a real provider key is wired in.
- **`src/ai/agents/rcaAgent.ts`** — `analyzeFailure()` would return a root-cause verdict (severity, priority, root cause, suggested fixes) for a failed test. The reporter only reaches this after `hasApiKey()` returns `true`; called directly, the stub throws.
- **`src/ai/agents/flakyAnalyzer.ts`** — `analyzeFlaky()` detects flaky tests **without needing an API key**: it deterministically diffs the current run's pass/fail status against the previous run, per test, and reports any test that flipped status. A configured API key only adds an optional LLM-generated summary on top of that diff.
- **`reports/runs/*.json`** — a small snapshot (`runId` plus per-test status) the reporter writes after every run, so the *next* run has something to diff against. This is generated output, git-ignored, and grows by one file per run.

Because the diff needs a previous run to compare against, the first run on a clean checkout prints `only one build recorded — run again to compare`; the flaky verdict appears from the second run onward.

To wire up a real provider, replace the stub in `hasApiKey()` with real key detection (e.g. reading `process.env.LLM_API_KEY`, or whatever variable name your chosen provider's SDK expects) and implement `analyzeFailure()` against that provider's API.

## Continuous Integration

CI is configured via GitHub Actions in `.github/workflows/playwright.yml`.

- **Triggers**: on `push` and `pull_request` to the `main` or `master` branches
- **Runner**: `ubuntu-latest`, with a 60-minute timeout
- **Steps**:
  1. Checkout the repository (`actions/checkout@v4`)
  2. Set up Node.js (`actions/setup-node@v4`, LTS version)
  3. Install dependencies with `npm ci`
  4. Install Playwright browsers with system dependencies (`npx playwright install --with-deps`)
  5. Run the full test suite (`npx playwright test`)
  6. Upload the HTML report as a build artifact (`playwright-report/`, retained for 30 days), even if the run fails or is cancelled

To view results from a CI run: open the workflow run on the **Actions** tab in GitHub and download the `playwright-report` artifact.
