# Advanced Framework Playwright

A TypeScript-based test automation framework built on [Playwright](https://playwright.dev/), scaffolded for scalable UI + API testing with page objects, fixtures, schema validation, and reporting.

## Framework Overview

This is a hybrid **UI + API test automation framework** built around Playwright's test runner and the **Page Object Model (POM)** pattern. Key characteristics:

- **Multi-environment aware** — `TTA_ENV` selects between `qa`, `stg`, `prod`, and `dev` base URLs, resolved automatically in `playwright.config.ts`
- **Data-driven** — test data can be sourced from CSV, XLSX, or JSON (via `csv-parse`, `xlsx`, `jsonpath-plus`), with synthetic data generated by `@faker-js/faker`
- **API-capable** — `src/api` holds API clients/helpers, and `ajv`/`ajv-formats` validate JSON schemas for response assertions
- **Custom reporting & logging** — a custom Playwright reporter (`src/utils/CustomReporter.ts`) generates a standalone HTML report (`tta-report/`) with test results and screenshot/video/trace artifacts, in addition to the built-in HTML/list reporters, Allure reporting, and Winston-based logging
- **AI-assisted analysis (optional, currently stubbed)** — `src/ai/` holds hooks the reporter calls for root-cause analysis on failures and flaky-test detection between runs; see [AI-Assisted Analysis](#ai-assisted-analysis-optional) below
- **Clean imports** — TypeScript path aliases (`@pages/*`, `@api/*`, `@fixtures/*`, etc.) avoid deep relative import chains
- **CI-integrated** — GitHub Actions runs the suite on every push/PR to `main`/`master` and uploads the HTML report as a build artifact

## Tech Stack

- **Playwright** (`@playwright/test`) — end-to-end test runner (Chromium, Firefox, WebKit)
- **TypeScript** — with path aliases for clean imports
- **Allure Playwright** — test reporting
- **Winston** — logging
- **Ajv / Ajv-formats** — JSON schema validation (useful for API response checks)
- **dotenv** — environment variable management
- **@faker-js/faker** — test data generation
- **csv-parse**, **xlsx**, **jsonpath-plus** — external/data-driven test data support

```
│   │   ├── agents/
│   │   │   ├── rcaAgent.ts        # Root-cause analysis for a failed test (stub — needs an LLM provider key)
│   │   │   └── flakyAnalyzer.ts   # Deterministic flaky-test diff between runs (no key required)
│   │   └── config/

│   ├── api/               # API clients/helpers
│   ├── config/            # Environment & framework configuration
│   ├── fixtures/          # Custom Playwright fixtures
│   ├── pages/             # Page Object Model classes (BasePage + one class per page/flow step)
│   ├── testdata/          # Static/generated test data (CSV, JSON, XLSX)
│   ├── tests/             # Spec files
│   │   └── login.spec.ts           # Login flow coverage
│   └── utils/             # Shared utility/helper functions
│       ├── UtilElementLocators.ts  # Reusable Playwright action/assertion wrapper (click, fill, waits, selects, ...)
│       ├── DataGenerator.ts        # Faker-backed test data (credentials, checkout customer info, full profiles)
│       ├── logger.ts               # Winston logger factory (`createLogger`) used across pages/specs
│       └── CustomReporter.ts       # Custom "TTA" HTML reporter (see Custom Reporter section below)
├── tta-report/            # Generated TTA HTML reports (git-ignored)
├── playwright.config.ts   # Playwright configuration
└── tsconfig.json          # TypeScript configuration + path aliases
```

Folders still empty are tracked with `.gitkeep` placeholders so the intended structure is preserved in version control until they're populated.

Page objects extend a shared `BasePage` (`src/pages/BasePage.ts`), which holds the Playwright `Page` handle and a `goto()` helper; individual page classes (`LoginPage`, `InventoryPage`, `ItemDetailPage`, `CartPage`, `CheckoutStepOnePage`, `CheckoutStepTwoPage`, `CheckoutCompletePage`) are scaffolded for a SauceDemo-style storefront flow (login → inventory → item detail → cart → checkout).

## Prerequisites

Make sure you have the following installed before setting up the project:

- [Node.js](https://nodejs.org/) v18 or later (LTS recommended) — includes `npm`
- [Git](https://git-scm.com/)
- A code editor with TypeScript support (e.g. [VS Code](https://code.visualstudio.com/))

```bash
node -v

git --version
```

## Setup

1. Clone the repository:

   ```bash
   git clone https://github.com/palkitrathod/Advanced_Framework_Playwright.git
   cd Advanced_Framework_Playwright
   ```

2. Install dependencies:

   ```bash
   npm install
   ```

3. Install Playwright's browser binaries:

   ```bash
   npx playwright install
   ```

4. Create your local `.env` file (see [Environment Configuration](#environment-configuration) below).

5. Run the sample test suite to verify the setup:

   ```bash
   npm test
   ```

## Environment Configuration

Environment variables are managed with `dotenv` and loaded automatically in `playwright.config.ts` from a `.env` file at the project root. `.env` is git-ignored, so each environment (local machine, CI, etc.) keeps its own copy.

Create a `.env` file in the project root with the following keys:

```
TTA_ENV=qa
BASE_URL=
QA_BASE_URL=
STG_BASE_URL=
PROD_BASE_URL=
DEV_BASE_URL=
API_BASE_URL=
LOG_LEVEL=info
TEST_ENV=QA
TEST_AUTHOR=
USERNAME=
PASSWORD=
```

| Variable | Description |
|---|---|
| `TTA_ENV` | Active environment key used to select which `*_BASE_URL` to run against (e.g. `qa`, `stg`, `prod`, `dev`) |
| `BASE_URL` | Default base URL of the application under test, used as the starting point for `page.goto()` calls |
| `QA_BASE_URL` | Base URL for the QA environment |
| `STG_BASE_URL` | Base URL for the Staging environment |
| `PROD_BASE_URL` | Base URL for the Production environment |
| `DEV_BASE_URL` | Base URL for local/dev environment (e.g. `http://localhost:3000`) |
| `API_BASE_URL` | Base URL for API test requests |
| `LOG_LEVEL` | Winston log verbosity (e.g. `info`, `debug`, `warn`, `error`) |
| `TEST_ENV` | Environment label used in test reports/logs |
| `TEST_AUTHOR` | Author tag used in test reports/logs |
| `USERNAME` | Login username for the application under test |
| `PASSWORD` | Login password for the application under test |

`.env` is git-ignored and never committed — treat `USERNAME`/`PASSWORD` and any future secrets as environment-specific and set them locally (or as CI secrets), not in source control.

> **Heads-up on `USERNAME`/`PASSWORD`:** `dotenv` never overwrites a variable that already exists in the environment. `USERNAME` in particular is set globally by some shells and CI runners, in which case the pre-existing value silently wins over your `.env` entry. If logins fail in CI but pass locally, prefix these keys (e.g. `TTA_USERNAME`/`TTA_PASSWORD`) to make them collision-proof. Reference these values via `process.env.<VAR_NAME>` in `src/config`, and add new variables here as the framework grows.

## Path Aliases

Configured in `tsconfig.json` (`compilerOptions.paths`) for cleaner, absolute-style imports instead of long relative paths (`../../../utils/...`):

| Alias | Path |
|---|---|
| `@api/*` | `src/api/*` |
| `@config/*` | `src/config/*` |
| `@fixtures/*` | `src/fixtures/*` |
| `@pages/*` | `src/pages/*` |
| `@testdata/*` | `src/testdata/*` |
| `@utils/*` | `src/utils/*` |

Example usage:

```ts
import { LoginPage } from '@pages/LoginPage';
import { getTestUser } from '@testdata/users';
import { UtilElementLocator } from '@utils/UtilElementLocators';
import { DataGenerator } from '@utils/DataGenerator';
```

> Note: `tsconfig.json` paths are used for type-checking and editor IntelliSense. If you introduce a build step or ship compiled JS, ensure the alias resolution also works at runtime (e.g. via `tsconfig-paths` or a bundler) or a test runner plugin that understands `paths`.

## Test Configuration

Defined in `playwright.config.ts`:

- **Test directory**: `./src/tests`
- **Base URL**: resolved from `TTA_ENV` (falls back to `BASE_URL`, then the matching `*_BASE_URL` for `qa`/`stg`/`prod`/`dev`/`api`)
- **Browsers/projects**: Chromium (Desktop viewport)
- **Timeouts**: `60s` per test, `10s` for expect assertions
- **Parallelization**: `fullyParallel: true`
- **Retries**: `0` locally, `2` on CI (`process.env.CI`)
- **Reporters**: HTML, list, and a custom reporter (`src/utils/CustomReporter.ts`, see [Custom Reporter](#custom-reporter) below)
- **Tracing/screenshots/video**: trace and video captured on every run; screenshots on failure only
- **Environment loading**: `.env` is loaded via `dotenv` before the config is evaluated, resolved as `path.resolve(__dirname, '.env')` so it is found regardless of the current working directory

## Running Tests

npm scripts are defined in `package.json` and are the recommended way to run the suite:

| Script | Command | Purpose |
|---|---|---|
| `npm test` | `playwright test` | Run all tests |
| `npm run test:headed` | `playwright test --headed` | Run with a visible browser |
| `npm run test:ui` | `playwright test --ui` | Open Playwright's interactive UI mode |
| `npm run test:debug` | `playwright test --debug` | Step through tests with the inspector |
| `npm run report` | `playwright show-report` | Open the built-in HTML report |

Pass extra Playwright arguments after `--`:

```bash
# Run a single spec file
npm test -- login.spec.ts

# Filter by tag
npm test -- --grep @p0

# Run a specific project/browser
npm test -- --project=chromium

# Headed, single spec
npm run test:headed -- login.spec.ts
```

> **Run from the project root.** `npx playwright test` only looks for `playwright.config.ts` in the *current* directory. Invoked from a subfolder such as `src/tests`, it silently runs with Playwright's defaults — no `baseURL`, no projects, no reporters — and relative navigations like `page.goto('/path')` fail with `Protocol error (Page.navigate): Cannot navigate to invalid URL`. The `npm` scripts above avoid this entirely, because `npm run` always executes from the package root regardless of where you invoke it.

## Custom Reporter

`src/utils/CustomReporter.ts` implements a self-contained "TTA" HTML reporter (`CustomTTAReporter`, registered as a default export and wired up in `playwright.config.ts`). Per run it writes to `tta-report/`:

- `report_<timestamp>.html` — the full standalone report for that run
- `index.html` — redirects to the most recent report, so it's safe to bookmark
- `history.html` — index of past runs
- `traces/`, `videos/` — per-test artifacts copied out of Playwright's results

It also prints a live per-test result line and a final summary table (pass/fail/skip counts, duration, pass rate) to the console.

### Viewing the report

```bash
open tta-report/index.html          # macOS — always the latest run
```

Embedded videos may be blocked by the browser over `file://`. If so, serve the folder over HTTP instead:

```bash
npx serve tta-report
```

Traces aren't viewable from the report directly — open them with Playwright's trace viewer:

```bash
npx playwright show-trace tta-report/traces/trace_1.zip
```

`tta-report/` is git-ignored, since a timestamped report plus trace/video artifacts are written on every run.

## AI-Assisted Analysis (optional)

`CustomReporter.ts` can enrich the report with AI-generated context for failed and flaky
tests, but everything under `src/ai/` is currently a **stub** — the hooks are wired up and
called from the reporter, but no real LLM backend is configured yet.

- **`src/ai/config/providers.ts`** — `hasApiKey()` is the single gate the reporter checks
  before calling any LLM path. It currently always returns `false`, so AI calls are skipped
  by design until a real provider key is wired in.
- **`src/ai/agents/rcaAgent.ts`** — `analyzeFailure()` would return a root-cause verdict
  (severity, priority, root cause, suggested fixes) for a failed test. The reporter only
  reaches this after `hasApiKey()` returns `true`; called directly, the stub throws.
- **`src/ai/agents/flakyAnalyzer.ts`** — `analyzeFlaky()` detects flaky tests **without
  needing an API key**: it deterministically diffs the current run's pass/fail status
  against the previous run, per test. A configured API key only adds an optional
  LLM-generated summary on top of that diff.
- **`reports/runs/*.json`** — a small snapshot (`runId` + per-test status) the reporter
  writes after every run, so the *next* run has something to diff against. This is
  generated output, git-ignored, and grows by one file per run.

To wire up a real provider, replace the stub in `hasApiKey()` with real key detection
(e.g. reading `process.env.OPENAI_API_KEY` or `process.env.ANTHROPIC_API_KEY`) and
implement `analyzeFailure()` against that provider's API.

## Continuous Integration

CI is configured via GitHub Actions in `.github/workflows/playwright.yml`.

- **Triggers**: on `push` and `pull_request` to the `main` or `master` branches
- **Runner**: `ubuntu-latest`, with a 60-minute timeout
- **Steps**:
  1. Checkout the repository (`actions/checkout@v4`)
  2. Set up Node.js (`actions/setup-node@v4`, LTS version)
  3. Install dependencies with `npm ci`
  4. Install Playwright browsers with system dependencies (`npx playwright install --with-deps`)
  5. Run the full test suite (`npx playwright test`)
  6. Upload the HTML report as a build artifact (`playwright-report/`, retained for 30 days), even if the run fails or is cancelled

To view results from a CI run: open the workflow run on the **Actions** tab in GitHub and download the `playwright-report` artifact.
